# 线上销货单对照后的优化整改方案

日期：2026-10-18。范围：独立工具tplus_sales_import。当前阶段仅分析和设计，没有修改应用程序或业务数据库。

## 1. 整改目标与边界

优先解决档案缺失、金额算法和业务默认值差异，使导入后的销货单在T+中的展示、计算与后续操作符合约定。最终验收按源用友单号和销售标识匹配，不能用自增ID或总金额单独判断。

用户已确认的要求继续有效：源用友单号去重；整单原子提交；坏单失败、其他单继续；保留零数量退货；客户税率来自客户档案；单位来自存货档案；不自动生成出库单、发票或凭证。当前十进制向零截断规则仍为有效规则，本文的线上兼容金额算法是待确认的变更建议，不是已经获准替换的规则。

## 2. 数据证据

- 线上5274单7566条，本地5243单7529条；共同5241单7527条。
- 共同数据中客户、结算客户、存货、单位、仓库、项目、业务类型、数量、税率、含税单价等无差异。
- 线上独有33单39条，本地客户档案缺失；本地独有2单2条均为数量0、金额0的销售退货，符合已确认保留规则。
- 共同7527条的含税金额线上比本地多1.90，未税金额多35.39，税额少33.49；两侧内部表头/明细合计均一致。
- 线上全量7566条未税金额全部符合ROUND_HALF_UP(G/(1+r),2)，税额为G-N。
- 线上7550/7566条含税金额符合源金额ROUND_HALF_UP(2位)，其余16条不符合；67.995实际67.99就是例外之一。二进制浮点round和十进制HALF_EVEN均不能解释全量。
- 线上7558/7566条未税单价符合ROUND_HALF_UP(G/Q/(1+r),8)。直接使用含税单价/(1+r)再四舍五入8位仅吻合7007条，单纯减少小数位不足以解决差异。
- 其余8条全部数量1、金额0，线上未税单价0.0001。该规律提示零金额最小单价处理，但尚不能证明其业务来源，不能自动扩展至所有零金额记录。
- 线上明细7566条taxFlag=1、isModifiedPrice=1、dataSource=2497、isSaleOut=15、refundDifferenceFlag=51185、isPresent=0、isManualCost=0。

## 3. 分阶段整改

### P0：先补档案和完善导入校验

1. 输出缺失客户编码去重清单及关联源单号、行数；从原账套补齐真实客户档案和客户税率枚举。新建档案ID允许与线上不同，必须重新按code映射；不复制业务单据中的外键数字作为新账套ID。
2. 客户编码为空的XKP0026202610122125仍拦截，补正源数据后再导入。线上也没有这张单，不能自动猜客户。
3. 对固定币种、营销机构、人员及所有缓存业务编码统一检查唯一性与有效状态；查询用户同时核对显示姓名/PersonName和配置固定姓名关系。已有唯一性保护继续保留。
4. 重新导入仍按ExternalCode跳过已有单据；仅补入此次新增合法单据，不更新或覆盖已有数据。当前SA流水按本地最大编号继续分配，不能复制线上旧编号导致冲突。
5. 零数量退货沿用保留，明确区分Q=0和Q!=0且G=0，后者可能触发线上0.0001单价例外。

验收：缺档补齐后原33单39条重新校验通过；空客户行继续明确标记；已导单据0重复、0覆盖。

### P1：将金额计算做成一个有版本的规则模块

集中计算含税金额、未税金额、税额、单价和表头合计，所有预览、实际写入、对账及恢复任务使用相同规则版本。任务JSON、日志和结果报告记录规则版本，防止同一源数据不同时间采用不同算法而无法追溯。

候选线上兼容规则：

| 项目 | 建议 | 证据及限制 |
|---|---|---|
| G：含税金额 | 保留源金额为依据；先确认16条例外的原系统算法 | 不改成数量乘单价；统一HALF_UP尚不能完全复刻线上 |
| N：未税金额 | HALF_UP(G/(1+r),2) | 全线上7566条吻合，但替换当前截断需业务确认 |
| T：税额 | G-N | 保持精确勾稽 |
| 普通未税单价 | Q!=0时HALF_UP(G/Q/(1+r),8) | 7558条吻合，金额为已确定G |
| Q!=0且G=0 | 保留专项规则入口并记录例外 | 8条线上单价0.0001，业务原因待核实 |
| Q=0 | 不做除法；保持当前可导入规则，单价按确认口径处理 | 线上无该类记录，不能从线上反推 |
| 表头金额 | 对最终明细G、N逐条求和 | 不用总含税额统一除税，避免行级尾差 |

不使用float作为新实现以追求偶然匹配；保留Decimal高精度中间值，只在规定的输出环节处理精度。正负金额对称测试，涵盖退货、极小金额、67.995、16条含税例外和8条零金额例外。

验收：明确区分“精确复刻线上”和“当前业务认可的统一规则”。未解释例外逐行列出，禁止以总金额接近或允许0.01误差掩盖字段差异。没有规则变更确认时，当前截断规则继续运行。

### P1：补全有依据的业务默认值合同

目前NULL与0/1混用是最需要处理的结构差异。按字段明确取值来源、类型、空值语义、是否枚举/外键，以及业务作用，再进入build_payload，而不是依赖数据库碰巧存在的默认值。

| 字段类别 | 建议处理 |
|---|---|
| 明细taxFlag | 将线上1列为候选必写值，在T+验证含税价解释、金额展示后落地 |
| 明细isModifiedPrice | 将线上1列为候选值，核实是否表示手工改价及后续重算影响；确认后显式写入 |
| isPresent、isManualCost及其他0类标记 | 按普通销售和退货分别确认，显式填0的字段须有业务依据，不能一律NULL转0 |
| dataSource=2497、refundDifferenceFlag=51185、isSaleOut=15 | 检查真实枚举归属和当前账套有效性；按语义映射，不按线上数字盲填 |
| isCarriedForwardOut/isCarriedForwardIn | 区分未结转0、已结转1和未知NULL；用户要求不生成出库单，状态必须与实际业务结果一致 |
| agency/agencyid、auditedtime | 查明对应人员及实际审核运行时间语义；不能仅为消差复制历史日期或人员外键 |
| auditor/auditorid/voucherState | 保留已确认固定审核信息，但区分写审核字段与执行完整T+审核流程 |

验证方式：在测试账套导入普通销售、销售退货、零数量退货、零金额非零数量各类样本；查看T+能否打开、打印、金额重算及业务状态展示。确认没有生成额外出库单、发票和凭证，再扩大范围。样本常量只能证明数据分布，不能独立证明业务含义。

### P2：成本、出库及系统关联字段按业务流程处理

costPrice/costAmount、latestCost、毛利相关字段、saleOutQuantity、docid及单据关联不得从其他单据复制。是否需要这些值取决于是否执行成本计算、库存及结转等业务；当前要求不生成出库单，不应把saleOutQuantity直接等同quantity或填造已出库状态。

若验收要求完整T+业务流程等价，需额外验证相关业务入口生成的关联和状态，当前直接写主明细的实现不能仅凭字段数量就声明等价。此项不在本方案中擅自扩大为生成出库/财务单据。

### P2：对账与性能优化

1. 主表业务键ExternalCode；明细业务键用友单号+销售标识。分类输出：缺档、缺单、数量差、金额差、状态差、预期ID/时间差；不要将几十万条系统字段差异淹没金额及缺单问题。
2. 每批提交前保留完整主从勾稽，加入最终确认的业务标记核对；提交后任务记录保留具体ID和算法版本。
3. 线上导出后续必须带列名，当前无列名文件按本地sys.columns顺序映射，虽然核心字段交叉匹配成立，仍存在列顺序变动的风险。
4. 在目标大表上先检查现有索引和执行计划，再评估ExternalCode、code和明细idSaleDeliveryDTO索引；只有确认重复数据、现有业务约束及索引重复情况后，才决定是否建唯一索引。不能凭单次耗时直接改生产索引。
5. 继续分批写入、完整单据二分隔离、同事务去重及主从原子提交、显式临时表清理。新增日志区分缓存、去重、INSERT主表、INSERT明细、对账、COMMIT和导出耗时，并记录候选单据/明细数。

## 4. 已导数据整改策略

程序后续调整不能自动修复当前已导数据：现有去重策略会跳过它们。这是必须单独处理的存量范围。

建议先生成只读修复预览：用友单号、明细标识、主键、旧值、新值、规则版本、原因和预计影响行数。将本次新增5166单与之前77张历史单区分，避免默认改写历史记录。预览还应显示明细/表头金额及税额差额，记录原值快照。

只有用户明确授权存量更新后，才采用完整单据事务修复，检测记录是否已被其他业务修改或关联、按最终明细重算表头并验证，出现冲突回滚该单并报告。不要直接删除重导，不重写IDENTITY，不更改源用友单号，也不以手动造关联的方式消除系统字段差异。

## 5. 推荐实施顺序和验收

1. 补齐客户档案、导出缺口清单：最快补齐业务数据覆盖，不改变当前金额算法。
2. 决定是否改为线上兼容金额规则，解决16条含税例外和8条零金额单价机制，再落地一个完整规则版本。
3. 核实并补齐taxFlag、isModifiedPrice等必要标记；其他枚举/状态分项验证。
4. 在测试账套按场景验证T+展示及不生成额外业务单据，完成对账。
5. 如需修改既有数据，先提交独立存量修复预览，再按授权实施。

验收不要求自增ID、时间戳、历史创建时间与线上相同；要求主从关联正确、合法单据覆盖完整、档案语义一致、金额遵循最终确认算法、表头明细精确勾稽、业务状态与实际处理一致，以及重复执行不重复写入。
